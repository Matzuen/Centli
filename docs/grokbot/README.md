# 交接说明：审计方 ↔ Grok Bot

> 更新日期：2026-10-17（Asia/Shanghai）
> 审计方：可跑 shell（只读审计 + 可自行验证 `git` / `flutter analyze` / `flutter test`）
> 编码方：Grok Bot（`D:\Program Files\Grok Bot\Grok Bot.exe`，可跑 shell、可读本仓库）

---

## 1. 分工

| 角色 | 职责 | 能力边界 |
|---|---|---|
| **审计方** | 只读审计、定位根因、写工单、复核 diff、**可自行跑验证** | 不改业务代码（只写工单与审计文档） |
| **Grok Bot** | 按工单写代码、跑验证、产出审计输入 | 可跑 shell、可读仓库、可写代码 |

**关键含义**：审计方**能独立复跑** `flutter analyze` / `flutter test`，
所以「Bot 报告通过但实际没通过」会被发现。
但审计方**看不到 Bot 的中间过程**，因此仍需要 Bot 产出审计输入（见 §3）。

> **经验教训（2026-10-16）**：曾发生「第 1 轮的修复从未被提交，后被批量提交覆盖 → 静默回归，
> 用户多忍受一轮错数」。故自 B1 批次起，**每个工单必须 `git commit` 并在 `notes.md` 贴出 hash**，
> 审计方会**同时核对 commit 与工作区**，不再只读文件。

---

## 2. 协作节奏

```
审计方出工单（BOT_TASKS*.md）
      ↓
Grok Bot 按工单改代码 → 每个工单一次 commit
      ↓
Grok Bot 产出审计输入（§3）
      ↓
   人工通知审计方
      ↓
审计方复核（含独立复跑 analyze/test + 核对 commit）→ 出不批工单
      ↓
Grok Bot 按新工单继续
```

**纪律**：

- **一个工单一次提交**。多个工单混在一个 diff 里会导致无法定位回归。
- 审计方给出的行号是**静态读码快照**，可能漂移。以当前文件内容为准定位。
- 若工单描述与现状不符（代码不存在、已修、或方向不对），**停下来报告**，
  不要自行决定替代方案。
- **不要提前做下一批的工单**（工单文件末尾会列"后续批次"，那是预告，不是本批任务）。

## 3. 审计输入清单（每轮结束时产出）

写入 `docs/grokbot/audit_input/`（该目录**不进版本库**，已在 `.gitignore` 中）。

### 3.1 必产出（缺一不可）

| 文件名 | 内容 | 生成命令 |
|---|---|---|
| `diff.patch` | 本轮全部改动 | 已提交：`git diff <上一轮commit> HEAD > ...`<br>未提交：`git diff > ...` |
| `status.txt` | 改动文件清单 + 新增/删除 | `git status --short > ...` |
| `analyze.txt` | 静态分析结果（**必须真实输出**） | `flutter analyze > ... 2>&1` |
| `test.txt` | 测试结果（**必须真实输出**） | `flutter test > ... 2>&1` |
| `notes.md` | 说明（见 §3.3） | 手写 |

### 3.2 建议产出

| 文件名 | 内容 | 说明 |
|---|---|---|
| `commits.txt` | 本轮各工单的 commit hash | `git log --oneline -N` |
| `untracked.txt` | 新增但未纳入 git 的文件 | `git status --porcelain --untracked-files=all` |
| `diff_stat.txt` | 每个文件的增删行数 | `git diff --stat` |

### 3.3 `notes.md` 应包含

1. **本轮对应哪些工单**（例如 `B1-1` ~ `B1-4`）
2. **每个工单的 commit hash** —— ⚠️ **强制项**（见 §1 教训）
3. **实际改了哪些文件、哪些行**（不要贴大段代码，`diff.patch` 里已有）
4. **是否有工单外的顺手改动** —— 如实列出并说明原因
5. **工单里的「择一」项，你选了哪个、为什么**
6. **你认为有风险或不确定的地方** —— **请诚实标注**，这比"看起来都改好了"有用得多
7. **`flutter analyze` / `flutter test` 是否真的全部通过**；若有不通过项，说明原因
8. **目视确认结果**（凡涉及界面的工单）：浅色 + 暗色下是否无溢出/无裁切

> **重要**：请勿伪造或美化 `analyze.txt` / `test.txt`。
> 审计方**会独立复跑**验证，隐瞒只会让问题在下一轮放大。

## 5. 审计方复核时会检查什么

收到 `docs/grokbot/audit_input/` 后，审计方会：

1. **commit 真实性** —— 每个工单是否**真的**有对应 commit（不只看工作区）
2. **越界检查** —— diff 是否触及工单外的文件（尤其顺手重构、整文件格式化）
3. **根因检查** —— 是修根因还是修症状
   （例：B1-2 若只是把某分类硬编码成 `'in'`，不算修好）
4. **边界覆盖** —— 每个工单列了边界情况，逐条对照
5. **新问题引入** —— 尤其：
   - B1-1 的"订阅流水"是否导致重复查询爆炸（性能已实测：3000 笔冷启动 38ms，不应过度设计）
   - B1-2 是否破坏了"分类被删/归档时回落支出"的路径
   - B1-3 是否让首页与资产页口径更不一致
   - B1-4 是否误改了 `assets_page.dart` 的**百分比**计算（那处不能动）
6. **验证真实性** —— **独立复跑** `flutter analyze` / `flutter test`
7. **测试补充** —— 检查断言是否有效（不是 `expect(true, true)`）

复核结果写成下一批工单或审计报告。
